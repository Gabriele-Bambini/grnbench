# EXP-20261018-GB-1: Does the `aracne3` adapter work against the real ARACNe3 program, and do its runs repeat?

## 1. Registration (before the run)

- type: **exploratory** (one subset of one dataset; a software check: no test, no score, no claim).
- owner: GB (agent-run)   issue: #109 (follow-up of #105; adapter in #106)   registered: 2026-10-18
- why: #106 rewrote the `aracne3` adapter from ARACNe3's source code (califano-lab/ARACNe3 at
  `3d8791a`: flags in `src/app/ARACNe3.cpp`, file formats in `src/app/io.cpp`) and tested it only
  against a stand-in for `subprocess.run` (`tests/test_aracne3.py`). This is the first build of the
  real program on the cluster and its first real call through the adapter. ARACNe3 never runs on a
  laptop.
- questions:
  - Q1: does `grnbench.infer.run_method("aracne3", adata, tf_list=...)` with `threads=1` exit 0 on
    the real program, with ARACNe3 reading as many samples as there are cells, writing
    `out/consolidated-net_grnbench.tsv` with the six columns the adapter expects, and the adapter
    parsing it into a non-empty network?
  - Q2: do two runs with the same seed and `threads=1` give byte-identical consolidated files?
  - Q3: with `threads=4`, do two runs with the same seed give identical files, and does the network
    equal the `threads=1` one? The module docstring says, from the source and not measured, that
    the null model need not repeat with more threads (`src/app/apmi_nullmodel.cpp`: the loop
    shuffles one shared vector inside `omp critical` and reads it outside).
- endpoints: Q1 pass or fail (ARACNe3's exit status, the sample count it prints, the file, its
  header, the adapter's status, edges > 0), with wall time and edge count. Q2 and Q3: sha256 of the
  consolidated file and of the cached null model of each run; edge by edge: shared edges, Jaccard,
  largest absolute MI difference, sign flips.
- unit: one subset of one dataset; descriptive only.
- data: `10x_pbmc3k/filtered/filtered_gene_bc_matrices/hg19/` (`matrix.mtx`, `genes.tsv`,
  `barcodes.tsv`; rows of `experiments/datasets.tsv`). Regulators: the sources of
  `references/collectri_human.tsv` in the cluster's setup cache. It only chooses the regulators:
  nothing is scored against it. The script records the sha256 of every input and whether it matches
  the registered row; the cluster's CollecTRI file differs in size from the registered one (D-020:
  live reference networks change between fetches), so a mismatch there is expected.
- subset (fixed now; the defaults of `benchmarks/aracne3_smoke.py`): 500 of the about 2,700 cells,
  drawn without replacement with `numpy.random.default_rng(0)`; `cpm_log1p` on all genes; of the
  genes detected in at least 10% of those cells, the 30 most variable CollecTRI sources and the 270
  most variable other genes (300 genes). The matrix goes in normalized (`assume_normalized=True`),
  as the engine hands it to every method; the 30 sources are the `tf_list`.
- runs (fixed now): seed 42 every time; `threads=1` twice (t1_a, t1_b), then `threads=4` twice
  (t4_a, t4_b); everything else at the adapter's and ARACNe3's defaults (one subnetwork, FDR with
  alpha 0.05, MaxEnt pruning). Comparisons: t1_a vs t1_b, t1_a vs t4_a, t4_a vs t4_b.
- fallback (fixed now): if t1_a keeps no edges (the adapter's "kept no edges" error), that is a
  result and is recorded; the four runs are then repeated once with
  `extra_args=["--alpha", "0.2"]`, the relaxation that error message names.
- exclusions: none. Comparison family: none (no statistical test).
- what counts as a defect of the adapter: a nonzero exit, ARACNe3 counting a number of samples
  other than the number of cells, no consolidated file, a header other than the six columns, or a
  parse error. Each gets a fix with a test on `gb/aracne3-cli` (#106). Differences between repeats
  are findings about ARACNe3, not defects of the adapter; they decide whether its `threads=1`
  default stays.
- figures: none. No network is scored or explained here (the run checks the adapter, not a model);
  `viz/index.md` of the results folder says so.

## 2. How it runs

- code: branch `gb/aracne3-cli` (#106) at the commit that adds this file, synced to a separate
  cluster checkout `~/grnbench-aracne3` (`hpc/hpc.sh sync`; its `GIT_COMMIT` is copied into the run
  folder as `CODE_COMMIT`). grnbench is imported from that checkout (`PYTHONPATH=src`; the script
  stops otherwise), not from the conda env's editable install.
- environment: conda env `grnbench` (`requirements/lock-py311.txt`), Python 3.11.17.
- ARACNe3: github.com/califano-lab/ARACNe3 at `3d8791a23e3bd8fd0d74f3b8d48f912e81d00f14`
  (2025-01-16), submodules at their pinned commits (Boost `214af4e5`, which is
  boost-1.83.0.beta1-24; googletest `455fcb77`). The cluster has no cmake (no binary, no module), so
  the build uses the official Kitware CMake 3.31.8 Linux binary (tarball sha256
  `630615d8e98ac33eba7fbe472626dff5c899c85af3c024585ae109166a6909d0`, checked against Kitware's
  published list) with the cluster's GCC 11.5.0 and its OpenMP, `-DCMAKE_BUILD_TYPE=Release`.
- login node, downloads only:
  ```
  git clone https://github.com/califano-lab/ARACNe3 ~/tools/ARACNe3
  git -C ~/tools/ARACNe3 checkout 3d8791a
  git -C ~/tools/ARACNe3 submodule update --init --recursive
  V=3.31.8; cd ~/tools
  curl -fsSLO https://github.com/Kitware/CMake/releases/download/v$V/cmake-$V-SHA-256.txt
  curl -fsSLO https://github.com/Kitware/CMake/releases/download/v$V/cmake-$V-linux-x86_64.tar.gz
  grep " cmake-$V-linux-x86_64.tar.gz$" cmake-$V-SHA-256.txt | sha256sum -c - && tar xzf cmake-$V-linux-x86_64.tar.gz
  ```
  On 2026-10-18 the submodule command stopped after about 75 clones: GitHub refused the remaining
  anonymous clones ("could not read Username for 'https://github.com'"). About 20 minutes later the
  89 missing Boost libraries were cloned one at a time, 15 s apart
  (`git -C ~/tools/ARACNe3/deps/boost submodule update --init -- <path>` per library), and the
  command above was run again to check every submodule out at its pinned commit. The build job
  refuses a tree with any submodule missing or off its pin.
- commands (from `~/grnbench-aracne3`, through `hpc/hpc.sh submit`):
  ```
  sbatch --export=ALL,CMAKE=$HOME/tools/cmake-3.31.8-linux-x86_64/bin/cmake hpc/aracne3_build.sbatch
  sbatch --export=ALL,OUT=$HOME/gb_runs/EXP-20261018-GB-1 hpc/aracne3_smoke.sbatch
  ```
  The second job runs `python benchmarks/aracne3_smoke.py --data-root ~/grnbench_data
  --aracne3-src ~/tools/ARACNe3 --out ~/gb_runs/EXP-20261018-GB-1`, with `GRNBENCH_ARACNE3_BIN` set
  inside the job only and the adapter's temporary folders on the node (`TMPDIR=/tmp/...`).
- machine: Bocconi HPC, partition and QOS `stud`, 4 CPUs, 8 GB, 1 h for each job.
- results: `benchmarks/results/EXP-20261018-GB-1/` (`summary.json`, `SUMMARY.md`, the subset lists,
  each run's consolidated network, ARACNe3's logs and messages, the two job logs; home paths written
  as `~`). The full run folder stays at `~/gb_runs/EXP-20261018-GB-1`.

## 5. Next

- `aracne3` can now be used by an experiment record; scoring it on real data needs its own
  (exploratory) record, on the HPC.
- `threads`: keep the default 1. With 4 threads the program took 1.841 s instead of 5.405 s here, but
  its null model did not repeat; callers who accept that can pass `threads=4`.
  - note 2026-10-22, added after the independent agent review of #106 (commit `61c9f89`): the adapter
    no longer passes the engine's generic `threads` to ARACNe3, because `grnbench infer`, `grnbench run`
    and `hpc/grnbench.sbatch` pass it to every method. The parameter for ARACNe3's `--threads` is now
    `aracne3_threads` (default 1): read `threads=4` above as `aracne3_threads=4`.
    `benchmarks/aracne3_smoke.py` passes its `--threads` entries as `aracne3_threads` from the commit
    that adds this note. The registered result is unaffected: it ran from code `6927b9f` (`CODE_COMMIT`), where
    `threads` reached ARACNe3, and nothing above was changed or rerun.
- one subnetwork (ARACNe3's default) leaves `count.values` and `log.p.values` constant and keeps
  some pairs with zero full-matrix MI; a scoring record should consider `extra_args=["-x", ...]`
  (more subnetworks) and declare it before its run.
