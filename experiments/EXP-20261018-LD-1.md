# EXP-20261018-LD-1: Does grnbench cisTarget pruning reproduce pySCENIC 0.12.1 on identical inputs?

## 1. Registration (before the run)

- type: **exploratory method validation**. This checks the implementation boundary behind
  `grnboost2_cistarget`; it is not a new biological or confirmatory claim.
- owner: LD   issue: #110   registered: 2026-10-18 (the commit adding this record is pushed
  before data preparation, model execution or `pyscenic ctx`).
- question: when the unmodified official pySCENIC 0.12.1 `ctx` command and grnbench receive the
  exact same processed expression matrix, full GRNBoost2 adjacency and registered cisTarget v10
  resources, do they generate the same activating modules and motif-supported TF-target pairs?
- rationale: grnbench documents `grnboost2_cistarget` as a NumPy implementation of pySCENIC step
  2. A direct reference comparison has not yet been recorded. The current grnbench Python 3.11
  lock cannot host pySCENIC 0.12.1 safely: the old package uses NumPy aliases removed in 1.24 and
  its published dependencies are not bounded for the current Dask/NumPy stack. Therefore the
  reference CLI runs unmodified in a separate Python 3.10 compatibility environment; grnbench
  remains in its registered environment.
- primary endpoint: exact equality of the final motif-supported TF-target pair set, after removing
  TF self-pairs from both implementations. Also report intersection, union, Jaccard, precision and
  recall with official pySCENIC as the descriptive reference.
- secondary endpoints: exact equality and the same overlap metrics for the union of activating
  module memberships; descriptive AUPRC ratio and EPR on the registered CollecTRI evaluation half
  after each supported set re-ranks the same full adjacency; counts outside that fixed adjacency
  universe; runtime and every terminal error.
- unit of analysis: dataset (n = 2): one human 10x 3' v2 breast dataset and one mouse 10x 3' v3
  primary-motor-cortex dataset. Exact task/arm/context/species rows are fixed in
  `EXP-20261018-LD-1.units.tsv`; both use the baseline `ctx0` artifact.
- datasets and reference snapshot: exact rows and sha256 values are fixed in
  `EXP-20261018-LD-1.snapshot.tsv`; the two CELLxGENE download rows are also in
  `EXP-20261018-LD-1.datasets.tsv`. These are approved bytes already registered for
  EXP-20261002-LM-1: two `data.h5ad`, their `truth.json`, human and mouse CollecTRI, four cisTarget
  v10 rankings and the matching HGNC/MGI annotations. No new data source is introduced.
- fixed-input contract: `real_bench.py` first produces the processed baseline `ctx0`, evaluation
  half and kept top-20,000 GRNBoost2 artifact. `pyscenic_compare.py prepare` then recomputes the
  **full** GRNBoost2 adjacency with seed 42 and must reproduce every pair and weight in that kept
  prefix (`rtol=1e-12`, `atol=1e-14`) before exporting one expression TSV and one adjacency TSV.
  Both implementations consume those exact exported files. A failed gate is a terminal failure,
  not a reason to substitute inputs.
- pySCENIC reference: PyPI/Git tag 0.12.1, invoked through its public `pyscenic ctx` CLI with the
  published defaults: activating modules only, thresholds 0.75/0.90, top 50 targets, top
  5/10/50 regulators, minimum 20 genes, no dropout masking, rank threshold 5000, AUC threshold
  0.05, NES threshold 3.0, custom multiprocessing. `pyscenic_reference_export.py` imports the same
  package's `modules_from_adjacencies` only to export its upstream modules for diagnosis; it does
  not patch or reimplement pySCENIC.
- exclusion and failure rules (fixed now): no dataset replacement and no post-result exclusion.
  A missing or hash-mismatched registered file, failed fixed-input gate, pySCENIC import/CLI error,
  empty module/regulon result, timeout or OOM is retained as a terminal error. One resubmission of
  the exact same clean commit/output is allowed only for a scheduler interruption or timeout;
  a deterministic package error is not retried or hidden. No source patch, monkey patch or silent
  dependency substitution is allowed. A compatibility-environment failure within two working days
  is itself the recorded limitation requested in issue #73.
- comparison family and test: no inferential family and no p-value (exploratory n = 2). All metrics
  are descriptive per dataset; the two datasets are never treated as edges, cells or genes for an
  inferential sample size.
- interpretation fixed now: exact equality on both datasets validates the documented equivalence
  for these inputs; any non-equality identifies a semantic divergence to diagnose in a separate
  issue before changing production code. Reference-recovery differences are diagnostic only and
  cannot establish which implementation is biologically superior.
- seeds: reference split 0, cell subsample 0, GRNBoost2 42; pySCENIC `ctx` step has no stochastic
  model fitting because the adjacency is fixed.

## 2. How it runs

- code: clean commit containing this record on `ld/pyscenic-comparison`; `hpc/hpc.sh sync` writes
  its hash to `GIT_COMMIT`, and both Slurm jobs copy it to their output. The hash is filled from
  the actual pushed pre-registration commit, never guessed here.
- environments:
  - grnbench: cluster `grnbench` conda env, Python 3.11,
    `requirements/lock-py311.txt`, editable code forced to the synced checkout by `PYTHONPATH`;
  - official reference: separate `grnbench-pyscenic-0.12.1` conda env, Python 3.10,
    `requirements/pyscenic-0.12.1-py310.txt`. The resolved `pip freeze --all` is stored with the
    large run output. It is never installed into the grnbench environment.
- pre-launch correction (2026-10-18): the initial reference environment setup attempt on HPC
  failed before any model or Slurm job ran because the cluster's default conda channel lacks
  `pip=23.3.2` (`PackagesNotFoundError`). `hpc/setup_pyscenic_env.sh` was corrected to pull that
  exact bootstrap package from `conda-forge` (`conda create -y -c conda-forge -n "$ENV_NAME" python=3.10 pip=23.3.2`).
  All registered scientific package versions in `requirements/pyscenic-0.12.1-py310.txt`, data,
  metrics, seeds, and the experiment design remain completely unchanged; this is an operational
  bootstrap correction, not a biological result.
- data preparation on the login node (downloads/copies only; hard links avoid duplicating the
  registered cisTarget files):
  ```bash
  D=~/grnbench_data_pyscenic_ld1
  CACHE=~/grnbench_data
  mkdir -p "$D"
  python benchmarks/fetch_cellxgene.py --out "$D/cellxgene" \
    --from-manifest experiments/EXP-20261018-LD-1.datasets.tsv
  mkdir -p "$D/references" "$D/cistarget"
  cp -al "$CACHE/references/collectri_human.tsv" "$CACHE/references/collectri_mouse.tsv" \
    "$D/references/"
  cp -al "$CACHE/cistarget/hg38_10kbp_up_10kbp_down_full_tx_v10_clust.genes_vs_motifs.rankings.feather" \
    "$CACHE/cistarget/hg38_500bp_up_100bp_down_full_tx_v10_clust.genes_vs_motifs.rankings.feather" \
    "$CACHE/cistarget/mm10_10kbp_up_10kbp_down_full_tx_v10_clust.genes_vs_motifs.rankings.feather" \
    "$CACHE/cistarget/mm10_500bp_up_100bp_down_full_tx_v10_clust.genes_vs_motifs.rankings.feather" \
    "$CACHE/cistarget/motifs-v10nr_clust-nr.hgnc-m0.001-o0.0.tbl" \
    "$CACHE/cistarget/motifs-v10nr_clust-nr.mgi-m0.001-o0.0.tbl" "$D/cistarget/"
  python benchmarks/data_manifest.py "$D" \
    --check experiments/EXP-20261018-LD-1.snapshot.tsv --require-all
  bash hpc/setup_pyscenic_env.sh grnbench-pyscenic-0.12.1 "$PWD"
  ```
- exact plan and Slurm commands (QOS `stud`: first job running, dependent second job queued; never
  more than two submitted jobs):
  ```bash
  O=~/gb_runs/EXP-20261018-LD-1
  python benchmarks/real_bench.py plan --data-root "$D" --out "$O/real_tasks.json"
  J1=$(sbatch --parsable --time=24:00:00 \
    --export=ALL,REPO_DIR=$PWD,OUT=$O/real,SCRIPT=benchmarks/real_bench.py,TASKS=$O/real_tasks.json,REFS=$D/references,CHUNK=100000,MODELS=grnboost2,KEEP_ARTIFACTS=1,GRNBENCH_CISTARGET_DIR=$D/cistarget \
    hpc/engine_bench.sbatch)
  J2=$(sbatch --parsable --dependency=afterok:$J1 \
    --export=ALL,REPO_DIR=$PWD,SOURCE_RUN=$O/real,OUT=$O/comparison,CISTARGET_DIR=$D/cistarget \
    hpc/pyscenic_compare.sbatch)
  printf 'real_bench=%s comparison=%s\n' "$J1" "$J2"
  ```
- machine: Bocconi HPC, partition/QOS `stud`; one 8-CPU, 32-GB real-benchmark job followed by one
  8-CPU, 48-GB comparison job, each capped at 24 hours. No compute runs on the login node.
- results: large processed matrices, full adjacencies, pySCENIC logs and resolved environment stay
  in `~/gb_runs/EXP-20261018-LD-1/`. Only the generated portable directory from
  `comparison/portable/` goes to `benchmarks/results/EXP-20261018-LD-1/` after privacy/size checks.
- generated outputs: `COMPARISON.json`, `COMPLETE.json`, `REPORT.md`, `viz/index.md` and PNGs,
  `latex/report.tex`, all written by `benchmarks/pyscenic_compare.py report`. Completion requires
  2/2 manifest units terminal; permanent errors remain in the report.
- status at registration: no dataset downloaded for this experiment, no model run and no HPC job
  submitted. Issue #110 is claimed but does not receive label `running` until `J1` is accepted.

## 3. Results (filled by scripts, not by hand)

- status: **done**
- produced by: HPC Slurm job 707418 (`gb-engine`, elapsed 12:50, exit code 0:0) and dependent job 707419 (`gb-pyscenic`, elapsed 13:15, exit code 0:0), executed from clean commit `b555c56` on branch `ld/pyscenic-comparison`.
- headline: on identical expression matrices and full GRNBoost2 adjacencies, the separately
  exported union of activating-module pairs is identical between grnbench and pySCENIC 0.12.1
  (human Jaccard 1.0000, 20,974 pairs; mouse Jaccard 1.0000, 27,596 pairs). The registered primary
  endpoint was not met: final motif-supported pairs diverge (human Jaccard 0.4291, 3,911 vs 4,055
  pairs; mouse Jaccard 0.5778, 7,278 vs 8,385 pairs). Treating pySCENIC only as the set-overlap
  reference, grnbench precision is 0.6116 human and 0.7881 mouse; its descriptive CollecTRI AUPRC
  ratio is 1.3262 vs 1.2762 human and 1.4682 vs 1.4645 mouse. Neither descriptive comparison
  establishes biological superiority.
- all declared comparisons: recorded in `benchmarks/results/EXP-20261018-LD-1/REPORT.md` and `benchmarks/results/EXP-20261018-LD-1/COMPARISON.json`.
- verdict: **primary endpoint not met; final motif pruning exhibits semantic divergence**. The
  secondary union of activating-module pairs matches exactly, but it comes from a separate
  `modules_from_adjacencies` export rather than from the final `ctx` output and therefore does not
  validate full pySCENIC step 2 equivalence. The motif-enrichment pruning divergence should be
  diagnosed in a focused follow-up issue before altering production code.
- figures: `benchmarks/results/EXP-20261018-LD-1/viz/index.md` (`implementation_overlap.png`, `reference_recovery.png`).
- generated report: `benchmarks/results/EXP-20261018-LD-1/latex/report.tex`.
- deviations from section 1: pre-launch bootstrap correction (2026-10-18): `hpc/setup_pyscenic_env.sh` was updated to pull `pip=23.3.2` from `conda-forge` because cluster default channel lacks it. All registered scientific package versions, data, metrics, and seeds remained unchanged.
- post-run wording correction (2026-10-25): review identified that the earlier result text called
  the separately exported pair union "activating modules" and did not state explicitly that the
  registered final supported-pair endpoint failed. The generated numbers and files are unchanged;
  the two uncommitted adjacency counts were removed from the narrative so every cited number is
  checkable in `COMPARISON.json`.
